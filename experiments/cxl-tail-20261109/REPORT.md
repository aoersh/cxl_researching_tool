# CXL 尾延迟先导实验报告

**2026-11-11 更新：** 完整结论、用户 sudo 数据分析、24 组新增对照和待办见 [最终报告](FINAL_REPORT_20261111.md)。本文的数字和方法范围为最初 54 组实验；其“尚未同步采集”的描述记录当时状态，后续结果以最终报告为准。

## 结论

现有工具已经足以完成“CXL 驻留数据访问的尾延迟测量、不同 NUMA 路径比较、读写竞争敏感性分析和初步 PEBS 归因”。不必先安装更多工具才能开始研究。

但目前还不能把每次尖峰精确拆解为 CXL 链路传输、设备排队、设备 DRAM、TLB、调度和中断各自的耗时；也没有应用请求级 P99/P99.9 的证据。PCM 的带宽曲线不能替代访问延迟分布。

## 机器与实验范围

- CPU：Intel Xeon 6515P，Granite Rapids，family 6 / model 173，双路，每路 16 个物理核，共 32 核 / 64 线程，标称 2.3 GHz。
- 系统：Ubuntu 22.04.5，Linux 6.8.0-138-generic；perf 6.8.12；MLC 3.13。
- node0 / node1 为两路 CPU 的 DRAM；node2 / node3 为各 64 GiB 的无 CPU CXL NUMA 节点。
- 全部延迟探针固定 CPU0：node0 为本地 DRAM，node1 为跨路 DRAM，node2 为本地 CXL，node3 为跨路 CXL。
- 本次运行时间跨 2026-11-09 和 2026-11-10。目录名保留首次实验日期；逐次墙钟和单调时钟记录在 `runs/*/run.json`。
- 共 54 组有效实验：30 组直方图主实验、12 组关闭直方图的平均延迟对照、12 组 PEBS 开关配对测试。失败的试运行保存在 `pilot/`，不计入结论。
- 全部由普通用户运行，没有执行 sudo、安装软件、重启或修改全局 sysctl/governor。

## 方法

MLC 主实验：随机依赖指针追逐，256 MiB 工作集，`--idle_latency -e -r -c0 -jN -b256m -t3 -f4 --lat_hist_max_us=100`。`-e` 不修改预取器 MSR。随机性为 MLC 默认分块随机，不等同于整个工作集上的均匀随机。

每种条件重复 3 次，轮内顺序固定种子随机化。带载时另启 MLC `--loaded_latency -T`，在 CPU1–4 上每线程分配 256 MiB，按配置绑定指定节点。读负载使用 `R`，写负载使用 `W6`（非临时写）。CPU32 是 CPU0 的 SMT 同胞，未安排带载线程。

探针不与持续读写线程共享物理核。带载程序还有 CPU0 协调线程：额外验证显示，其初始化后两个相隔 3 秒的快照中 CPU 时间保持不变；不把它宣称为不存在。后续仍须用调度轨迹排除短暂干扰。

原定带载 12 秒不足以覆盖部分实际测试，失败轮次已排除并用 30 秒带载补测。MLC 的 `-t3` 不保证进程在 3 秒内退出；初始化、校准、按批执行和输出都有额外时间。每次进程生命周期和观测区间单独记录。

同时采集：CXL 设备 PMU 的读写 CAS 计数（1 秒区间）、`/proc/PID/numa_maps`、`smaps_rollup`、线程亲和性/运行统计、软件 perf 计数及系统 vmstat 前后差值。

直方图共有 **482,914,560 条计数**。按每次 MLC 输出的 base MHz（2299 或 2300）将周期桶换算为 ns；桶宽约 6.96 ns。以下 P99 等为三次运行分位桶端点的中位数，不是合并分位数，也不是置信区间。平均列为 MLC 单次平均值的三次中位数，不是单独筛选 CXL 未命中后的平均。

### 可以支持的判断

1. 同设备竞争显著放大本地 CXL 尾延迟。P99.9 从约 0.68 µs 升至读竞争约 2.54 µs、写竞争约 3.96 µs，约为基线的 3.7 倍和 5.8 倍。
2. 不能只看平均值：写竞争的平均值低于读竞争，但 P99 和 P99.9 更差。两者负载类型和实际流量不同，不能据此推导等带宽条件下写必然比读更差。
3. 将同样四个带载核改为访问本地 DRAM，CXL P99.9 保持约 0.69 µs。相比“仅仅多了四个忙核”，结果更支持同设备/共享路径上的资源竞争解释；但尚未定位具体排队环节。
4. 本地 CXL 的访问延迟超过 1 µs 的比例：基线约 0.038%，同设备读竞争约 45.8–46.3%，同设备写竞争约 20.2–20.4%。精确上下界在 `group-summary.csv`。
5. 跨路 CXL 的平均值在带载后下降，但尾部仍升高。这说明平均值不代表尾部，也提示频率、uncore/链路省电状态或访问路径状态可能随负载变化；本次没有同步频率/驻留数据，不能把原因写成已证实。

### 重复性与边界

- node2 空载三次 P99.9 的分位桶整体覆盖 668–681 ns；读竞争覆盖 2492–2567 ns；写竞争覆盖 3946–3979 ns。
- 主实验各次均观察到目标缓冲区全部落在指定节点，4 KiB 页，`AnonHugePages=0`；探针稳态快照亲和性为 CPU0。
- 探针没有 major fault，但整机 vmstat 部分区间有其他 major fault/NUMA 迁移，不能声称整机完全无活动。
- 软件计数覆盖初始化和测试全生命周期；约 6.5 万次 minor fault 主要对应初始落实页，不能全部归为测量期缺页。MLC 也有初始化/校准期迁核，不能把全程 `cpu-migrations` 直接解释为稳态探针跑偏。
- 观察到数百至上千次非自愿上下文切换，但无事件级时间关联，尚不能判断具体尖峰是否由调度造成。
- 所有直方图合计有 263 条进入约 100 µs 以上溢出桶；不能给出这些访问的精确最大值，更不能直接归因于 CXL 硬件。
- P99.99 已保存，但先导实验只有每条件三次短运行、跨两个日期、系统电源状态未固定，不把它当成稳定 SLO 或可泛化硬件规格。

## PEBS 的实际可用程度

在 node2 上使用独立的 128 MiB 全范围随机指针追逐探针，先后运行不采样/采样配对，各 5 秒，空载和四线程读竞争分别重复三次。该工作负载与 MLC 的分块随机不同，二者数值不直接等同。

采样事件：`cpu/mem-loads,ldlat=64/upp`，`precise_ip=2`，请求虚拟地址、物理地址、数据来源与 latency weight，采样周期 257。

- 共得到 4769 条样本，其中符号为 `chase` 的 4427 条；4392 条物理地址有效，全部属于 region0 范围 `[0x1080000000, 0x2080000000)`；35 条物理地址为零，未发现有效地址落入其他区域。
- 六次采样均报告 Lost Samples=0；原始记录中未发现 `PERF_RECORD_THROTTLE`。这不意味着硬件无采样偏差或每个长延迟事件都被捕获。
- 空载 `chase` 样本 3427 条，读竞争只有 1000 条。每次带载约 332–335 条，不足以估计可靠 P99.9。
- 空载样本 weight 中位数约 1266–1269 cycles，读竞争约 3397–3415 cycles，支持竞争下访问 use-latency 上升这一方向性结果。
- PEBS 开关配对的平均延迟变化：空载约 −1.21% 到 +0.92%，带载约 −0.16% 到 +0.10%；处于本次重复波动范围。不能据此声称完全没有测量开销或尾部扰动。
- perf 可能将 CXL 访问解码为 `PMEM hit`，这是数据来源编码名称，不证明设备为持久内存；依据物理范围和拓扑确认 CXL。
- CXL 驻留页的 cache hit 不等于一次 CXL 事务。地址范围筛选回答“访问哪个内存区域”，数据来源筛选才帮助区分缓存命中与更远层级。
- `ldlat=64` 筛选的是特定延迟阈值以上的候选访问，weight 为 CPU 侧 use-latency，不能当作全体访问无偏分布，也不能按固定 2.3 GHz 直接换算成纯设备 ns。

之前已验证精确指令采样及 store 采样可以运行；本轮新增的是内存 load 的竞争对照，未声称重新验证所有 PEBS 事件。

## PCM 与 CXL 设备 PMU

本轮普通用户启动 PCM，虽然退出码为 0，却因 MCFG/TPMI 权限报错、检测到 0 个 CXL units，并出现 PMU programming 错误。因此不能把这次输出当成有效 CXL PCM 数据。完整访问仍需你在真实终端执行 sudo。

你此前的 root PCM CSV 已保存为 `previous-pcm-cxl-node3.csv`：node3 负载对应 Socket1 / CXL port0，稳定读段约 11,754 MB/s，写段约 4616 MB/s。证明已安装的 PCM 具备 CXL.mem 分端口带宽观测能力，但它不是本轮尾延迟测试的同步采集证据。

本轮成功使用普通用户 `perf stat` 读取设备 PMU：node2 对应 `cxl_pmu_mem0.0`，node3 对应 `cxl_pmu_mem1.0`，读写负载的计数方向相符。事件记录在每次 `pmu.csv`。这些是设备计数，尚未核对厂商语义/每事件字节量，未擅自乘 64 转换成带宽。

MLC 报告的四线程吞吐中位数：node2 顺序读约 13,611.9 MB/s，非临时写约 11,727.9 MB/s；node3 顺序读约 18,731.3 MB/s。它们是带载程序整段测得的吞吐，不是 PCM 同步总线字节数，也不证明达到链路物理上限。

PCM 能观察 CXL.mem / CXL.cache 的分端口、分方向流量；检测出端口单元不意味着每个端口都接有设备。现有 CXL.cache 为零不能证明其观测无效或不受支持。CXL.io 可考虑 `pcm-iio`，但本次未验证。`pcm-latency` 的 occupancy/inserts 指标不是逐访问 P99/P99.9，不能替代直方图。
